### R01：本地免登录不能由环境变量代替真实网络边界

- **位置**：`code/package.json:10–12`；`code/modules/auth/local-auth.ts:9–19`；`code/modules/runtime/runtime-config.ts:13–20`；`code/modules/auth/request-auth.ts` 的 `getRequestUserAsync()`。
- **触发与风险**：`dev:local` 只设置 `LOCAL_BIND_HOST=127.0.0.1`，没有给 `next dev` 传 `--hostname`。校验函数只相信该变量，Local 请求直接获得 `local-user`。同网段可达时，其他人可能读取/修改笔记、导出或删号；实际外部可达性仍取决于防火墙。请求级没有 Host 校验，也留下 DNS rebinding 的条件，但本轮没有执行浏览器 rebinding 攻击。
- **复现**：用独立 SQLite 和空素材目录运行 `npm run dev:local -- --port 3419`。`lsof` 显示 `TCP *:3419 (LISTEN)`，启动输出列出 Network 地址。只向 `127.0.0.1` 发请求，附加 `Host: review.invalid:3419`，`/api/session` 返回 `authenticated:true`、`local-user`、`csrfToken:local-mode`。生产构建的隔离实例也接受该 Host。
- **修复边界**：本机开发入口显式绑定回环；本地身份和本地素材入口在请求边界拒绝不受信任 Host/Origin。容器内部监听 `0.0.0.0` 与宿主机回环端口映射是不同层，保留当前 Docker 拓扑所需能力，不能简单全局禁止容器内部通配监听。
- **验收**：默认开发命令不再监听 `*`；合法回环访问、hydration、读写和两模式 e2e 正常；非本地 Host 在取得身份或正文前被拒绝。覆盖 IPv4、IPv6、localhost，以及反向代理转发头的信任边界。

### R02：发布工作流没有依赖测试结果

- **位置**：`.github/workflows/release.yml:3–61`；`.github/workflows/quality.yml:3–7`；`code/docker/Dockerfile:7–11`。

- **修复边界**：让发布针对待发布 SHA 等待并验证双模式检查、模式 e2e、边界与依赖门禁；随后才给予发布 job 必要的写权限。不要求加入新的部署平台。
- **验收**：在隔离分支/测试仓库制造测试失败和依赖审计失败，均不能推送发布产物；通过后可发布且 provenance 指向同一 SHA。只检查 YAML 语法不算完成。

### R04：认证适配器没有履行事务契约

- **位置**：`code/modules/auth/better-auth-adapter.ts:617–619`。已安装 Better Auth 的 `dist/db/internal-adapter.mjs` 中 `createOAuthUser()` 通过事务组合创建 user/account。
- **复现**：在 `adapter.transaction(async tx => { await tx.create(user); throw new Error(...) })` 中注入失败，捕获异常后 `SELECT COUNT(*) FROM users` 仍为 **1**。方法只是 `return callback(adapter)`，没有 BEGIN/COMMIT/ROLLBACK。
- **风险**：OAuth 多步写入失败留下半成品身份，导致重试或后续登录异常。尚未在真实 GitHub 故障下复现账户锁死；普通成功路径 e2e 抓不到此类失败原子性问题。
- **修复边界**：实现符合异步回调、并发请求和嵌套行为要求的事务接口，或明确采用库支持的安全替代；不能直接用同步 `better-sqlite3.transaction()` 包住未等待的 Promise。
- **验收**：user 写入后 account 写入失败时两者均不残留；成功时全部提交；并发登录与重试不互相提交/回滚；原有字段最小化和 token hash 约束保持有效。

### R05：认证读操作全表扫描并在 JS 中过滤

- **位置**：`code/modules/auth/better-auth-adapter.ts:253–275,290–309,471–505`。
- **证据**：查一个 session 仍执行无 WHERE 的 `SELECT ... FROM sessions` + `.all()`，然后逐行 hash/过滤；查 user/account 同样全表读取。表虽然有唯一索引，但这条路径用不到。
- **合成测量**：查询同一个不存在的 session token，100 行平均 **0.29 ms**，10,000 行平均 **10.85 ms**，各 10 次。本机数据说明增长趋势，不是生产容量或攻击吞吐结论。
- **风险**：用户/会话增长后，鉴权放大 CPU、内存和同步 SQLite 工作，影响同进程所有用户。过期会话不应依靠每个旧 cookie 再被访问才清理。
- **修复边界**：将允许字段和操作映射到参数化 SQL，在数据库做过滤、排序、limit/offset；保留 token 哈希查找，不拼入任意字段名。按实际策略处理过期会话，先确认库自带行为。
- **验收**：查询计划命中适当索引；小/中/大合成规模的鉴权延迟有可接受预算；不把全表结果拉到 JS；保留会话过期、登出、用户隔离和删号测试。

### R06：状态只限制单字段，没有限制累计资源

- **位置**：`code/app/api/state/route.ts:129–215`；`code/modules/learning-state/repository.ts` 的 `saveNote()`、`createStageOutcome()`、`getStateSnapshot()`；`code/app/api/data/route.ts:68–90`。
- **复现**：用 Local Mode 一次性库，提交 100 个目录中不存在的 `scopeId`，每条 20,000 字符，全部 **200**；快照达 **2,020,758 bytes**。API 只有按用户每分钟写入次数限制；条目、阶段、任务 ID 没有对照权威目录，笔记/成果等没有累计条数/字节预算。
- **风险**：Cloud 已登录账户同样经过这些仓库方法，可持续增长共享 SQLite；部分写入还全量返回快照。耗尽磁盘、内存或串行处理时间后会影响其他学习者。本轮没有制造磁盘耗尽或线上压测。
- **修复边界**：在服务端核对目录 ID（兼顾退场 ID 的历史状态策略）；为个人状态设置合理条数/字节限制；敏感写入不附带无界全量数据，快照/导出采用有界策略。具体容量先由维护者确认，不引入收费计量系统。
- **验收**：未知 ID、超预算写入得到明确 4xx 且不落库；合法既有状态可读写/导出；并发请求不能越过预算；超大请求在读取完整 JSON 前受大小限制。登录限流不替代存储配额。

### R07：备份健康不检查备份年龄和恢复验证年龄

- **位置**：`code/modules/admin/admin-health.ts:215–236`；`code/modules/observability/privacy-monitor.ts` 的 `alertsFor()`。
- **复现**：真实创建一份时间标记为 `2020-01-01` 的有效加密备份，`restoreVerifiedAt:null`；健康摘要仍返回 `backup.status:"ok"`。判断仅检查 manifest、文件大小与 SHA-256，不使用时间阈值。告警只处理明确上报的 backup/restore 失败，任务从未运行或静默停摆不会自动成为失败事件。
- **风险**：备份调度失效后持续呈现健康，事故时只能恢复陈旧状态。该问题不同于“线上定时备份是否已部署”，后者本轮无法确认。
- **修复边界**：为备份年龄、缺失恢复验证、演练陈旧设置独立状态/阈值，阈值对齐部署方的 RPO 和演练政策；无需站内新增消息平台。
- **验收**：可控时钟测试最新/超时/未来/无效时间、没有备份、未验证和已验证；停止备份后外部监控能识别超时；错误口令/篡改反向对照继续有效。

### R08：恢复的“不得覆盖已有目标”没有原子保证

- **位置**：`code/modules/learning-state/backup.ts:244–277`。
- **触发**：先 `stat(target)` 判断不存在，再写临时库和检查，最后 `rename(temp,target)`。两步之间另一个恢复进程或应用可创建目标；POSIX rename 会替换它。已有静态目标会被拒绝，因此常规恢复演练仍通过。
- **复现**：仅在临时目录，故障注入器在最终 rename 前模拟另一个进程创建目标文件，真实恢复函数返回 `verified:true`，并发目标内容被覆盖。此为确定性并发事件注入，**不是在运行中的数据库上做破坏实验**。
- **风险**：维护操作并发时覆盖新建的数据；旁边已有 WAL/SHM 也必须纳入“干净目标”判定。没有证据表明历史恢复已经丢数据。
- **修复边界**：使用目标文件系统支持的原子 no-clobber 安装方案与目标占用检查，明确定义跨平台行为；不能只在 rename 前再做一次 stat。
- **验收**：两个恢复进程争同一目标只允许一个成功；在安装前创建目标时恢复失败且目标逐字节保持；有活动 WAL/SHM 时拒绝危险目标；既有三组反向对照继续通过。

### R09：私人状态库创建权限过宽，依赖父目录偶然保护

- **位置**：`code/modules/learning-state/state-store.ts:37–40`；`code/modules/learning-state/database.ts:238`。备份文件已单独采用 0600，这里是运行状态库。
- **复现**：当前 umask `0022`，一次性状态库目录为 **0755**、库文件 **0644**。API 没有加密运行中的 SQLite，文件包含私人笔记和身份数据；会话 token 已哈希，不能因此直接声称文件中有明文 token。
- **风险与限制**：部署在可遍历的共享目录/主机上时，本地其他 OS 用户可能绕开 HTTP 鉴权读取个人数据。当前本机用户 home 实测为 **0700**，本轮没有证明另一个账户可穿过该 home 读取日常数据库；应修复的是新建路径缺少自身最小权限约束。
- **修复边界**：新建状态目录/库及 WAL/SHM 明确设定仅服务身份可访问；已有文件权限迁移需保留正确 owner，不移动数据库文件、不破坏 Docker 卷。磁盘加密是否启用另行核验，不能用 chmod 代替。
- **验收**：宽松 umask 下仍创建安全权限；同机另一个普通用户在可遍历父目录下不能读库；服务与同卷维护容器可备份恢复；不手工拆分 SQLite 状态单元。

### R10：缺少私人响应缓存与页面防嵌入策略

- **位置**：`code/app/api/state/route.ts`、`code/app/api/data/route.ts`、`code/app/api/session/route.ts`；`code/next.config.ts:3–9`；`code/scripts/lighthouse-deploy.sh:718–723` 与生产 Runbook Caddy 示例。
- **实测**：生产构建 `/api/state` 返回 200，但没有 `Cache-Control`；首页虽由框架输出 `private,no-store`，却没有 CSP/frame-ancestors、X-Frame-Options 等。应用和所检查的 Caddy 模板没有补齐策略。
- **风险与边界**：私人状态和导出应明确禁止被缓存；账户删除、进度确认等页面缺少防嵌入约束会增加点击劫持风险。未证明当前部署的 CDN/代理会缓存这些数据，也未实际执行点击劫持。Next.js 的 `force-dynamic` 不是所有客户端和中间层的禁止缓存指令。
- **修复边界**：为身份、状态、导出、管理员响应设置明确的 private/no-store；按 HTML/API/图片分别定义安全头。CSP 需兼容 Next.js 实际脚本和阅读器，不可未经验证全局套用导致 hydration 失败；HSTS 仅在真实 HTTPS 域名上确认策略后设置。
