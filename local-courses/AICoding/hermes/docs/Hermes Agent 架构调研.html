1.1 Hermes 是什么

Hermes 是一个面向个人场景的统一 AI Agent 运行时——同一套 Agent 内核（对话循环、工具调度、记忆系统、技能管理）无差别部署于 CLI、消息网关（~20 平台）、TUI 与桌面端四种前端，平台差异完全收敛在适配层。内核以窄腰为设计哲学：核心工具集保持极简，能力通过 Skill、Plugin、MCP 在边缘扩展。内置跨会话记忆、子代理委派、Cron 调度与真实终端/浏览器驱动，并以 Prompt Caching 字节稳定性作为全局约束。

⚙

跨会话学习

三层记忆（SessionDB / MEMORY.md / 外部 Provider）+ 技能自进化（Curator 自动整合归档），Agent 跨会话持续积累经验

✚

子代理委派

隔离上下文 + 独立预算，支持单任务与批量并行；orchestrator 角色可链式编排（最大生成深度=2）

⏱

1.3 两大核心设计原则

Hermes 的所有架构决策几乎都在为这两个原则服务。理解它们，就拿到了理解全报告的钥匙。

原则 1 对话中缓存前缀不可破坏

问题：每次调用 LLM API 时，整个对话历史（System Prompt + 历史消息）都要发给模型。一段 20 轮的对话，每轮都重新发送全部内容，费用极高。

解决：LLM 供应商支持缓存命中——如果本轮发送的内容与上一轮的前缀完全相同，这部分按 1 折计费。对话越长，缓存命中越多，费用越低。

后果：一旦对话中途修改了历史消息、切换工具集、或重建 System Prompt，前缀就变了，缓存全部失效——费用立刻翻 10 倍。因此 Hermes 把"对话中绝不修改已发送内容"作为铁律。唯一例外是上下文压缩（压缩后重建等价的新前缀）。

一句话：对话开始后，前面的内容一个字都不能改。

原则 2 核心尽量小，功能尽量放外面

问题：Agent 每次调用 LLM 时，所有工具的定义（名称、参数、描述）都会附在请求中一起发送。工具越多，每次请求的 token 越多，费用越高、模型注意力越分散。

解决：把"必须每次都带的核心工具"（终端、读文件、搜索）控制在最小集合。新能力按成本从低到高的顺序选择交付方式：

  • CLI 命令 + Skill — 零 token 成本，Agent 通过终端执行
  • 条件门控工具 — 配置了才出现，没配置就不占 token
  • Plugin — 独立安装，按需启用
  • MCP Server — 外部进程，按需连接
  • 核心工具 — 最后手段，每个用户每次调用都要付费

一句话：能用插件解决的不用核心工具，能用命令解决的不用工具。

1.3b 六大架构亮点

⚙

窄腰设计

核心 Agent 只保持最小接口——对话循环、System Prompt、工具分发。新能力通过 Skill、Plugin、MCP Server 扩展，不污染核心。Footprint Ladder 确保每个新能力选择最小永久占面的方案。

🔒

缓存优先架构

Prompt Caching 是所有架构决策的首要约束。三层 Prompt 分离、冻结 Memory 快照、日期级时间戳、角色交替修复——每个设计都服务于"会话内 System Prompt 字节不变"这一目标，唯一例外是上下文压缩。

🌏

边缘可扩展

20+ 消息平台、8 个 Memory Provider、7 种终端后端、无限 MCP Server——全部通过统一 ABC + Orchestrator 模式接入，新平台 / Provider 无需修改核心。

🔄

闭环学习循环

跨会话自改进：经验积累 → 技能自创建 → 使用中 patch 改进 → Curator 后台治理 → 跨会话回忆。Agent 越用越好，大多数框架会话结束即遗忘。

🧠

三层记忆架构

L1 SessionDB（FTS5 全文搜索）+ L2 MEMORY.md / USER.md（冻结快照注入 Prompt）+ L3 外部 Provider（8 个可插拔）。冻结快照保证缓存与记忆共存。

⚖

边缘激进，核心保守

产品在边缘激进扩张——新平台、新渠道、新 Provider 都是目标；核心保守克制——每个新模型工具都要随每次 API 调用发送，门槛极高。"最小占面"管的是能力如何接入核心，不是产品能不能长。

同步循环的设计含义

循环是完全同步的——从 LLM 调用到工具执行到下一轮迭代，顺序执行不并行。Gateway 的多用户并发通过线程级隔离实现（每会话一个线程），而非协程级。单个 Agent 会话内因此不需要锁，但迭代预算仍用线程锁保护，因为子代理委派时父子共享预算。

4.1 Context 构建总览

每次调用 LLM API 时，发送的完整请求由两个独立层面拼接而成。它们的生命周期、构建时机、缓存策略完全不同，理解这一区别是理解 Hermes 缓存机制的基础。

Context 构建两层面 — 会话级 vs 轮次级
会话级 — System Prompt
• 构建时机：首轮构建一次，之后缓存复用
• 生命周期：整个会话不变（唯一例外：压缩时重建）
• 内容：Agent 身份 · 行为指引 · 技能索引 · 工具感知 · 环境/平台提示 · Memory 快照 · 时间戳
• 缓存效果：作为请求前缀，命中后按 1 折计费
• 字节稳定性：时间戳仅含日期，同一天内字节一致
轮次级 — Messages 列表
• 构建时机：每轮 API 调用前组装
• 生命周期：随对话增长，逐轮追加
• 内容：历史消息（user / assistant / tool）· 当前轮用户输入 · 工具结果 · 临时上下文注入
• 缓存效果：追加在缓存的 System Prompt 之后，前缀部分仍命中
• 临时注入：插件上下文 / Memory 预取结果注入当前轮 user 消息，不修改历史
= 完整 API 请求
[System Prompt 缓存] + [Messages 列表 逐轮增长] + [Tools Schema]
为什么分两层？
① 缓存命中的分界线就在两层之间——System Prompt 是稳定前缀，Messages 是增长后缀。只要 System Prompt 不变，前缀部分就一直命中折扣价。
② 临时上下文只注入轮次级——插件预取、Memory 结果、网关通知等易变内容写入当前轮 user 消息，绝不修改 System Prompt，避免前缀失效。
③ 压缩是唯一重建 System Prompt 的时机——压缩后生成新的等价前缀，代价是缓存失效一次，但换回继续对话的能力。

4.2 API 调用前的消息处理流水线

每次调用 LLM 前，存储的 messages 列表经过一条六步净化流水线，生成一份仅供 API 使用、不回写存储的副本 API 消息列表。目标：保证发给 API 的消息角色合法、内容干净、前缀字节稳定。

为什么所有处理都在副本上？

存储的 messages 是会话真相——持久化到 SQLite，包含 reasoning 供 UI 回放。API 副本 API 消息列表 是一次性投射：剥离内部字段、注入临时内容、规范化字节，用完即弃。这保证净化逻辑不会破坏存储的对话历史，也不会因为格式化导致跨轮前缀不一致。

字节规范化为什么重要？

本地推理引擎（llama.cpp / vLLM / Ollama）的 KV-cache 按精确字节前缀匹配。如果同一消息在两轮中序列化结果差一个空格或 key 顺序不同，缓存就 miss。⑤ 用 排序键 + 紧凑分隔符确保同一 tool_call 在每一轮序列化出完全相同的字节，让本地部署也能享受缓存加速。

工具 schema 每次调用都附在 API 请求中，直接影响 token 成本和模型注意力。①②③ 决定了带哪些工具；④ 决定了哪些工具真正可见（没配 API Key 的工具不会出现）；⑤ 保证模型看不到调不了的工具（避免幻觉调用）；⑥ 保证本地部署模型也能解析；⑦ 在工具过多时折叠非核心工具，把 token 还给对话。

5.1 上下文引擎 ABC

上下文压缩是 Hermes 中唯一允许在对话中途修改历史上下文的操作。压缩引擎通过 上下文引擎 ABC 实现可插拔，默认实现在 上下文引擎模块 中。

核心配置参数（config.yaml → compression）

  • 阈值 — 压缩阈值，默认 0.50（上下文窗口 50%）
  • 阈值令牌数 — 绝对 token 上限，默认 None；设置后取 min(比例阈值, cap)
  • 目标比例 — 尾部保留量 = threshold × 0.20
  • 保护前N条 — 默认 3，保护前 N 条消息不被压缩
  • 保护后N条 — 默认 20，保护最近 N 条消息不被压缩
  • 最大尝试次数 — 默认 3，压缩重试轮数上限（硬限 10）

可插拔设计

上下文引擎 是 ABC 接口，压缩策略可替换。插件可注册自定义压缩引擎。默认实现使用 LLM 生成结构化摘要。

5.3 压缩阈值机制详解

压缩触发的核心公式：阈值令牌数 = (上下文长度 - 最大令牌数) × 阈值百分比。其中 上下文长度 - 最大令牌数 是有效输入预算（扣除了输出预留）。但实际生效的 阈值百分比 并非简单取配置值，而是经过三层 raise-only 提升 + 绝对 cap四步计算。

阈值计算流水线（4 步，raise-only）
① 读取用户配置
压缩阈值 默认 0.50（50%）。这是基准值，后续步骤只升不降。
② 每模型路由覆盖
检查当前模型是否有专属阈值，取 max(用户配置, 模型专属)：
• Arcee Trinity → 75%   • GPT-5.4/5.5/5.6 Codex OAuth → 85%（Codex 硬限 272K）   • GPT-5.3-codex-spark → 70%（原生 128K）
③ 小上下文地板
窗口 < 512K 时 raise 到 ≥ 75%。防止 128K~262K 模型在 50% 时反复抖动——留太少余量给压缩后的 summary。
③b 退化保护
当 64K 地板 ≥ 有效窗口时，退化为 85%。确保小模型用满大部分上下文再压缩，而非在 50% 就触发导致浪费一半窗口。
④ 计算 阈值令牌数
(上下文长度 - 最大令牌数) × 阈值百分比，结果 floor 到 64K（大模型不过早压缩）。若 floor ≥ 窗口则取 85%。
④b 应用绝对 cap
若用户设了 阈值令牌数 绝对值，取 min(比例阈值, cap)。确保压缩不晚于用户指定 token 数，无论窗口多大。

5.4 压缩判定函数 + 反抖动保护

压缩判定函数 在判断是否需要压缩时，除了 token 阈值检查，还通过三重反抖动保护防止压缩风暴：

Summary-LLM 失败冷却

如果上一次压缩的 LLM 摘要生成失败，进入 600 秒冷却期，期间不再尝试 LLM 压缩。

防止 Summary-LLM 服务不可用时反复重试。

无效压缩计数

连续 2 次压缩节省不到 10%（无效压缩）后暂停压缩。

防止对无法有效压缩的对话反复尝试。

Fallback 压缩计数

连续 2 次 fallback 压缩（LLM 不可用时的降级策略）后暂停。

Fallback 质量低，连续使用意味着需要人工介入。

9.12 凭据文件传递 — 远程沙箱的凭据安全

路径遍历防护

拒绝绝对路径和 .. 序列。验证目录内() 确保 host_path 在 HERMES_HOME 内。恶意 所需凭据文件列表 被拒绝。

读 Deny-List

即使路径在 HERMES_HOME 内，.env、认证文件、MCP 令牌目录、Bitwarden 明文缓存也被拒绝挂载。技能可挂载自己的 token，不能挂载主密钥文件。

Bind mount 跟随 symlink，恶意 symlink 可暴露任意主机文件。安全技能路径() 检测 symlink 后，创建一个只含常规文件的临时副本用于挂载。

9.14 Profile 隔离 + 委派/Cron 隔离

Profile 隔离

  • 独立 config.yaml / .env / sessions.db / MEMORY.md
  • 独立 skills/ / plugins/ / logs/ / gateway
  • 应用配置覆盖() 在任何模块导入前设置 HERMES_HOME
  • 所有路径通过 获取主目录() 获取，永不硬编码 Hermes 主目录

Token 锁

获取作用域锁(范围, 标识) 防止两个 Profile 使用相同凭据（如同一 Telegram bot token）。锁文件含 PID + start_time + identity_hash。陈旧检测：PID 不存在 / start_time 不匹配 / 进程 cmdline 非 gateway / 进程已停止。原子陈旧锁移除防止竞态。

委派（Delegation）隔离

  • 独立上下文 — 不继承父对话历史
  • 独立终端会话 — 各自 task_id
  • 独立预算 — 子代理不挤占父代理 iteration budget
  • 角色限制 — leaf 不能 delegate/clarify/memory/send_message/cronjob
  • 深度限制 — 最大生成深度（默认 2）
  • 工具集交集 — 子代理只能用父代理启用的工具子集

Cron 隔离

  • skip_memory=True — Memory Provider 不运行
  • 独立 Cron 会话 — 不镜像到 Gateway 会话
  • 3 分钟硬中断 — 防止失控 Agent 垄断调度器
  • 上下文变量 清除 — 防止通知路由到源 chat
  • 威胁模式扫描 — prompt 注入检测
  • 文件锁 — .tick.lock 防止跨进程重复 tick

渐进式安全总结

Hermes 的隔离是渐进式安全：默认安全基线 + 按需加固。最弱配置（local 后端 + yolo 模式）适合开发调试；最强配置（Docker + 网络隔离 + egress proxy + 凭据 deny-list + 审批严格模式）适合生产环境。每一层都是独立可组合的——用户根据威胁模型选择需要的层。

三层并发守卫保障

① 活跃会话集（asyncio.Event per 会话键）— 适配器级，同 会话键 串行化。② 运行中智能体集（Dict per 会话键）— Runner 级 agent 实例锁。③ 会话轮次租约注册表（asyncio.Lock per session_id）— 转录层，同 session_id 串行化。三层守卫均按 会话键 / session_id 隔离，Cron 与用户会话的 key 不同，因此不会触发任何串行化。

Cron 结果投递不经过会话守卫

Cron 完成后直接调用 适配器.发送() 发送结果（线程安全调度器 跳转到 asyncio 线程），不经过 处理消息() / 活跃会话集 / 运行中智能体集。即使此刻用户正在与 Agent 对话，Cron 结果也能正常发出——它是纯出站消息，不创建 agent turn，不排队。

12.2 子系统协作总览

输入阶段

Gateway 接收消息 → Session 管理定位会话 → 双重守卫决定排队还是立即处理。

上下文构建阶段

turn_context 初始化 → MCP 刷新工具 → Memory 加载快照 → System Prompt 恢复或新建。所有子系统在此阶段协同准备 Agent 运行所需的完整上下文。

执行阶段

Agent Loop 迭代 → LLM 调用 → 工具分发（Registry / Agent 级）→ Memory 读写 → 压缩检查。这是循环的核心，可能多轮迭代。

输出阶段

最终响应提取 → Memory 后台同步 → Session 持久化到 SQLite → 流式响应发送到平台。

缓存贯穿全程

Prompt Caching 是贯穿所有阶段的不变量：System Prompt 字节稳定、角色交替严格、无循环内合成 user 消息、压缩后缓存安全重建。

设计之美

Hermes 的架构之美在于：所有子系统（Gateway、Memory、MCP、Skill、Tool、Cron、Compression）通过统一的 Agent 核心协作，核心保持窄腰，能力分布在边缘。一条消息的旅程穿越了几乎所有子系统，但每个子系统只做自己的事，通过明确定义的接口交互。

13.1 什么是闭环学习循环

闭环学习循环（Closed Learning Loop）是 Hermes 区别于所有其他开源 Agent 框架的核心标志。大多数 Agent 框架在会话结束后即"遗忘"一切——下次对话从零开始。Hermes 则构建了一个跨会话的自改进系统：Agent 从经验中创建技能、在使用中改进技能、通过后台 Curator 治理技能生命周期、并利用 FTS5 全文搜索和用户建模实现跨会话回忆。

核心定义

闭环学习循环 = 经验积累（Memory + Session 搜索）→ 技能创建（复杂任务后自动生成）→ 使用中改进（patch/edit 自迭代）→ 后台治理（Curator 状态流转 + LLM 审查）→ 跨会话回忆（FTS5 检索 + 用户建模注入）→ 回到经验积累，形成闭环。

🔄

越用越好

每次复杂任务完成后自动生成可复用技能，下次遇到类似任务时直接调用改进后的技能，而非从零推理。

📚

跨会话记忆

三层 Memory 体系 + FTS5 全文搜索 + Honcho 辩证用户建模，让 Agent 真正"记住"用户偏好和历史上下文。

🧮

自我治理

Curator 后台系统自动追踪技能使用情况，归档陈旧技能，通过 LLM 审查整合碎片技能为伞形结构。

三层 Memory 体系

  • 用户画像文件 — 用户偏好、习惯、工作方式
  • 会话数据库 — SQLite 存储全部对话历史与快照

缓存友好设计

所有经验数据在会话开始时冻结为快照，注入 Prompt Volatile 层。会话期间不再修改，确保缓存前缀稳定；新经验在会话结束后异步写入，下一会话才生效。

14.1 架构亮点

⚙

窄腰设计

核心 Agent 保持最小接口——对话循环、System Prompt、工具分发。所有新能力通过 Skill、Plugin、MCP Server 扩展，不污染核心。Footprint Ladder 确保每个新能力选择最小永久占位的方案。

🔒

缓存优先架构

Prompt Caching 是所有架构决策的首要约束。三层 Prompt 分离、冻结 Memory 快照、日期级时间戳、角色交替修复——每个设计都服务于\"会话内 System Prompt 字节不变\"这一目标。

🌏

边缘扩展性

20+ 消息平台、8 个 Memory Provider、7 种终端后端、无限 MCP Server——所有扩展通过统一 ABC + Orchestrator 模式接入。新平台/Provider/Memory 后端无需修改核心。

14.2 关键设计不变量

1. Prompt Caching 神圣不可侵犯

会话内 System Prompt 字节不变。唯一例外是 Context Compression——它是\"必要的缓存破坏\"。压缩后仍检查是否可保留原 Prompt。

2. 消息角色交替严格

永不连续两个同角色消息。每次 API 调用前修复角色违规。压缩时 summary 角色智能选择。Steer 注入到 tool 消息而非新建 user 消息。

3. Profile 完全隔离

每个 Profile 拥有独立的 HERMES_HOME。所有路径通过 获取主目录路径 获取，永不硬编码 Hermes 主目录。Token 锁防止跨 Profile 凭据冲突。

4. 无循环内合成 user 消息

Steer 注入到 tool 结果。临时上下文通过 sidecar 注入 API 副本，不进入持久化的 transcript。Slash 命令默认延迟生效（--now 可立即但牺牲缓存）。

5. 插件不碰核心

插件在独立目录中工作，通过 ABC + Hooks 接入。不修改 智能体运行模块、CLI 模块、网关运行模块。需要更多能力时扩展通用插件接口。

6. .env 仅限密钥

所有行为配置在 config.yaml。.env 只存 API Key / Token / Password。内部需要 env var 时从 config.yaml 桥接。

14.3 设计哲学总结

边缘激进，核心保守

Hermes 在边缘激进扩展——新平台、新渠道、新 Provider、新模型、新桌面/TUI 功能都是目标。在核心保守克制——每个新增的 Model Tool 在每次 API 调用中发送，门槛极高。"最小占位"管的是能力如何接入核心，不是产品能不能增长。

ABC + Orchestrator 模式

当多个插件实现同一类能力时，设计统一 ABC + Orchestrator，而非逐个合并竞品 PR。这让竞争实现可以共存，用户自由选择。

God-file 渐进拆分

智能体运行模块 和 CLI 模块 从单体巨文件拆分为 100+ 个聚焦模块。原文件保留为薄转发层，保持 API 兼容。大重构 PR 可安全合并。

16.2 IterationBudget — 迭代预算控制器

功能怎么做

Hermes 的 迭代预算控制器（迭代预算模块，62 行）是一个线程安全的迭代计数器，用于控制 Agent 对话循环的最大迭代次数。每个 核心对话实体 实例（父 Agent 或子 Agent）持有一个独立的 迭代预算控制器：

  • consume() — 消耗一次迭代，返回 True 表示预算未满、可以继续；返回 False 表示预算耗尽
  • refund() — 退还一次迭代（用于 代码执行工具 程序化工具调用轮次，这些轮次不应消耗预算）
  • remaining — 查询剩余迭代数
  • grace call — 预算耗尽后，宽限调用标志 标志允许模型再做最后一次尝试

父 Agent 上限来自 最大迭代数（默认 90），每个子 Agent 独立上限来自 委派.最大迭代数（默认 50）——子 Agent 不挤占父 Agent 预算。

技术细节

# 迭代预算控制器 — 线程安全的迭代计数器
# 初始化：设置最大迭代总量，已用计数归零，创建线程锁
# 消耗预算() → bool：加锁后检查是否已达上限，未达则计数+1返回True，已达返回False
# 退还预算() → None：加锁后检查是否有已用计数，有则计数-1（用于程序化工具调用的退款）
# 线程安全：所有读写操作都在锁保护下完成

线程安全

线程锁 保护 已用计数 计数器。支持多线程并发调用（Gateway 的 线程池执行器 场景）。

零依赖

仅用 Python 标准库 线程模块，无第三方依赖。62 行代码完全自包含。

分级预算

父 Agent 和子 Agent 各自持有独立预算。子 Agent 消耗不减少父 Agent 剩余——总迭代可超过父上限。

Delegation 父子委派

20.3 缓存失效机制

System Prompt 的缓存失效遵循最小破坏原则：仅在压缩时标记失效，并在重建前做一次"乐观检查"——如果缓存的 Prompt 已包含最新 Memory 内容，则跳过重建。代价越高的操作，越要避免。

缓存失效决策流
正常运行
缓存的 System Prompt 原样回放，每轮字节一致，KV-cache 命中。
压缩触发失效
压缩是唯一合法的失效源。标记缓存为 None，同时从磁盘重新加载 Memory 快照。
乐观检查：缓存 Prompt 是否已包含最新 Memory？
逐块验证当前 Memory 渲染结果是否逐字出现在缓存 Prompt 中。含 usage header，任何条目变更或字符数变化都会打破包含关系 → 触发重建。同时检查是否有残留的空 Memory 块头 → 有则视为过时。
已包含（快路径）
保留原 Prompt 不变 → 本地 KV-cache 前缀完好 → 零重建开销。失效标记是信号，不是强制命令。
已过时（重建路径）
从磁盘重新加载 Memory 快照 → 重建三层 Prompt → 更新缓存 → 持久化到 Session DB。缓存前缀失效一次。
正常运行 / 触发 检查 / 判断 保留 / 重建 条件路径
为什么用"包含检查"而不是"快照比对"？

在 fresh-agent 场景（Gateway / TUI 新进程恢复会话），缓存的 Prompt 从 Session DB 恢复，可能早于本会话中途的 Memory 写入。此时 MemoryStore 在初始化时已加载了最新内容，前后快照相同——如果用 before/after 快照比对，会误判为"一致"并保留过时的 Prompt。逐字包含检查直接验证缓存 Prompt 是否嵌入了当前 Memory 的渲染结果，不受快照时序影响。

企业应用风险与难点
安全 · 合规 · 成本 · 运维 · 可靠性 · 组织适配

将 Hermes 从个人场景引入企业环境，需要正视以下六类风险与难点。每类风险标注了严重度和缓解方向。

21.1 安全与数据隔离

高风险 终端命令执行

Agent 可驱动真实终端，危险命令虽有三级审批（CLI 内联确认 · Gateway 暂存 · strict 威胁扫描），但企业环境中审批人可能不在实时链路上，导致任务卡死或被绕过。

缓解：强制 Docker 后端 + 网络出站白名单；生产环境禁用 local 后端；审批超时自动拒绝而非降级执行。

高风险 Prompt 注入

Memory 写入有双层威胁扫描，但 web_extract 抓取的外部内容、MCP Server 返回的工具结果中仍可能携带注入指令，诱导 Agent 执行非授权操作。

缓解：工具结果在送入 LLM 前统一过滤；高权限操作（文件删除、网络外发）走独立审批通道，不受 LLM 推理结果影响。

中风险 凭据泄露面

.env 存储所有 API Key / Token，Profile 隔离靠 HERMES_HOME 环境变量。多用户共享服务器时，进程级隔离不够——任何能读取该进程环境的用户都能拿到全部凭据。

缓解：企业部署应接入 Vault / KMS 等凭据管理服务，.env 仅存引导 token；运行时凭据从 Secret Manager 动态获取。

中风险 数据驻留

对话历史存 SQLite 本地文件，Memory 存 Markdown 文件。企业合规要求（GDPR / 数据不出境）下，这些文件的物理位置、加密、销毁策略需要额外管控。外部 Memory Provider（honcho / mem0 等）将数据发往第三方 SaaS，存在数据出境风险。

缓解：Profile 绑定到企业内网目录；Memory Provider 优先选自建后端（byterover / retaindb）；Session DB 启用 SQLCipher 加密。

21.3 成本控制

迭代预算失控

默认 90 次迭代上限，复杂任务可能每轮消耗数万 token。无全局成本上限——预算按迭代数计，不按美元计。

缓解：降低 max_iterations；引入 cost guardrail 插件在 pre_llm_call 检查累计 token 是否超阈值。

压缩 LLM 调用

压缩本身调用独立 LLM 生成摘要，max_attempts 默认 3 次重试。高频压缩场景下，Summary LLM 费用可能占总成本 20%+。

缓解：auxiliary 配置压缩专用低成本模型；调整 threshold 降低压缩频率。

委派成本倍增

子代理委派每个子任务独立 Agent 实例，批量并行（默认上限 3）时成本线性增长。orchestrator 链式编排（深度 2）可能触发 9 倍调用。

缓解：企业环境限制 max_spawn_depth=1；leaf 角色强制不携带重型工具集。

21.5 可靠性与边界行为

压缩信息丢失

压缩将中间消息替换为摘要、旧 tool 结果替换为 1 行 stub。在需要精确回溯"Agent 当时看到了什么"的合规场景，压缩后的会话无法完整还原。

缓解：合规关键会话设 threshold=1.0 禁用压缩；或压缩前自动导出完整 transcript 到外部归档。

Grace Call 非确定性

预算耗尽后的 grace call 只输出不调工具，但 LLM 在信息不足时可能产生"幻觉"回答。企业决策场景下，用户难以区分正常回答和 grace call 兜底回答。

缓解：监控 iteration_budget.remaining，低于阈值时在前端标注"低预算模式"；grace call 响应追加 disclaimer。

Curator 误归档

Curator LLM 审查可能误判活跃技能为 stale 并归档。虽有 tar.gz 备份 + 可恢复，但企业高频使用时归档会导致技能"消失"，影响业务连续性。

缓解：企业环境 curator.enabled=false 或仅 pin 关键技能；LLM 审查 pass 前人工确认。

Cron 3 分钟硬中断

Cron 会话 3 分钟硬中断可能导致长任务被截断。skip_memory=True 隔离了 Memory 但也意味着 Cron 产出无法自动进入记忆体系。

缓解：长任务拆分为多段 Cron 链（context_from）；或改用 terminal(background=True, notify_on_complete=True) 替代 Cron。

缓存保护不变量总结
四大不变量 · 违反后果 · 贯穿全系统的缓存安全约束

以下四条不变量贯穿 Hermes 的所有核心机制——Agent Loop、Context 构建、System Prompt 组装、压缩、Memory 体系。它们是 Prompt Caching 得以生效的底层保证，也是 Hermes 架构设计的第一约束。

A.1 四大不变量

1. System Prompt 字节稳定

构建一次，回放不变。时间戳仅含日期。唯一重建触发器是压缩。

2. 角色交替严格

永不连续两个同角色消息。每次 API 调用前修复 + 压缩时 summary 角色智能选择。

3. 无循环内合成 user 消息

Steer 注入到 tool 结果。临时上下文通过 sidecar 注入 API 副本，不进入存储的 transcript。

4. 压缩后缓存安全

压缩后重建 Prompt 时，若缓存已反映最新 Memory，则保留原 Prompt 保护本地 KV-cache。

A.2 违反缓存的后果

违反缓存的后果

任何在对话中途修改历史上下文、切换工具集、重建 System Prompt 的行为都会使缓存前缀失效。长对话中，缓存失效意味着每一轮都要重新处理整个上下文，成本可能增加数倍。这就是为什么 Slash 命令默认延迟生效（--now 可立即生效但牺牲缓存）。
