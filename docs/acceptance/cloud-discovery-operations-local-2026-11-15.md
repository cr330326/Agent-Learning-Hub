# 云端资讯维护链路本地复核

2026-11-15 继续核对未完成任务后发现：Lighthouse 的配置上传只保留旧 OAuth 变量，升级前备份与恢复演练仍使用单库流程，发布包缺少资讯维护入口，备份健康只扫描根目录单库 manifest。这些缺口已在本地修复并验证；没有操作远程主机。

## 本轮变更

- 配置上传保留飞书、模型、价格与 GitHub App 字段；私钥单独上传并重写远程路径，发布、状态及回滚使用只读私钥挂载。保留原有秘密权限校验和不输出值的规则。
- `cloud-maintenance.sh` 从部署容器识别两个真实命名卷和固定镜像，以该镜像运行编译后的维护工具，维护容器禁用网络。Lighthouse 对新发布调用双库路径，旧发布保留单库升级前备份兼容路径。
- 批次记录两库逐表行数，恢复核对计数及跨库引用，清空临时提取引用与 worker 心跳、复位任务租约、保留付费未知回执。恢复演练只有在正向恢复与三组反向对照全部通过后才记录验证时间。
- 保留按完整库对执行：7 daily/3 weekly，另保留最近已验证批次；未知文件或无效批次保留供核对。新备份不会清掉当日最近恢复证据。
- 备份健康同时验证两份密文、manifest 和批次；单库旧备份不能让已启用资讯库的部署报告备份正常。展示最近的完整恢复验证时间。
- 两份云端 Runbook 同步维护入口、暂存恢复、在线安装两个新卷及人工切卷边界；回滚检查状态卷及资讯卷是否匹配。

初次在线安装时发现恢复暂存库需要写入 SQLite 的 WAL/SHM，而只读挂载使在线 API 返回 `SQLITE_CANTOPEN`。暂存卷改为可写、数据库连接保持只读后通过；源加密备份始终只读挂载。新卷安装前校验两个目标均为空，并设置私有文件权限。实际安装与候选启动通过后才记入本报告。旧验收卷未切入真实部署，也未删除维护者卷。

本轮界面代码沿用 [r11 功能验收](./cloud-discovery-local-2026-11-15.md)，其 57/48 张版式、22 通过/2 项模式不适用和 25/25 功能回归仍按原范围引用；新增备份健康展示另有本轮截图。
